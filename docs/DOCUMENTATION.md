# 文档维护约定

## 分层与事实来源

- 根 README 面向使用者：下载、安装、功能边界和文档入口，不记录维护者机器路径、临时工作树状态或归档批次。
- 当前指南：用户指南、开发入口、CI/发布流程、来源与核查状态。命令以当前源码和锁文件为准。
- 发布记录：记录固定标签、提交和附件哈希，不把后续 main 的变化归到旧安装包。
- 历史证据：日期化测试、旧版、撤回功能和设计计划。保留原始语境，不将旧命令写成当前推荐。
- 原始许可证和锁定 NOTICE 不作文字润色；迁移引用时验证其原始哈希。

状态更新应区分：已实现、已测试、已发布、许可已确认。任何一项不能替代另外三项。
用户不需要的构建细节进入开发文档，未完成的源码或授权事项必须如实保留。

## 更新与验证

1. 修改功能或发布后更新对应的当前指南及导航；发布记录引用固定提交。
2. 执行本地链接检查：

   ```powershell
   node scripts/check-docs.js
   # 将历史断链也作为失败处理
   node scripts/check-docs.js --all
   ```

3. 执行 `git diff --check`，检查相对路径、标题锚点和改动范围。
4. 外链不由离线检查器验证；发布或更换下载链接时，单独核对 GitHub 元数据及实际访问。
5. 执行 `npm test`：文档回归同时核对当前指南中的 npm 命令与 `package.json`，
   以及旧版维护分支、固定基线和归档范围是否一致。

检查器覆盖根 README、两份原生安装声明、appliance/Wrapper/Web 导航、旧版隔离和 renderer 边界说明，
以及 docs 内 Markdown 的普通行内本地链接和标题锚点；不覆盖全部 Markdown 扩展、HTML 锚点或引用式链接，不是完整的 Markdown 解析器。
当前入口错误会失败；历史错误默认警告，`--all` 可用于完整治理验收。路径不存在的历史构建产物不应伪造文件来消除警告，应标明历史身份或改成文字。

历史文件尽量保留原路径，通过索引和状态标识分层；不要随意移动会被代码、脚本或测试引用的文档。
旧版隔离后，当前指南使用 `legacy/v1/` 的真实路径并指向独立维护检出；
历史正文中的旧路径与命令保留原始语境，不逐条替换成不可运行的归档命令。
本轮治理覆盖维护者首页与 docs；导入的上游 README、许可证原文及旧安装包使用的声明不作改写。它们不应被误当作当前用户指南。
未要求提交或推送时，只维护本地文件，不自动移动标签、重发附件或改变仓库可见性。
